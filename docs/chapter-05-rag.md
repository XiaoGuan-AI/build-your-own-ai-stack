# 第 5 章：RAG——让模型开卷考试

> 目标：给模型装上一个「随时更新的知识库」。学完本章，你将亲手实现检索增强生成的完整链路：
> **文档切块 → 向量化 → 相似度检索 → 拼 prompt → 基于上下文生成**。
> 代码：`code/ch05/rag.py`（约 200 行，零外部依赖）。

```bash
.venv/Scripts/python.exe code/ch03/train.py --demo                 # 先有个模型
.venv/Scripts/python.exe code/ch05/rag.py --query "什么是梯度下降"
.venv/Scripts/python.exe code/ch05/rag.py --query "KV Cache 是什么" --compare  # 对照无 RAG
```

---

## 5.1 为什么要 RAG：两个大模型的痛点

1. **知识截止**：模型训练完，世界还在变。问它 2026 年的事，它只会瞎编。
2. **幻觉**：不知道就是不知道，但模型会「自信地编」。医生敢信吗？

**RAG 的思路朴素得惊人：既然模型会编，那就把正确答案塞进 prompt 里——开卷考试。**

```
普通问答：问题 → 模型瞎编
RAG 问答：问题 → ① 从知识库检索相关文档 → ② 文档+问题拼成 prompt → ③ 模型照着文档回答
```

**为什么比重新训练好？** 换知识 = 改知识库文件，不用动模型。公司内部文档、实时数据、私有资料——全部通过 RAG 注入，这就是现在企业级 LLM 应用的主力架构。

---

## 5.2 链路第一步：文档切块

知识库不是一整块丢给模型的（模型窗口有限），要先切成**语义完整的块**：

```
一本 10 万字的技术书
   ↓ 按段落/章节切块
[「张量是带形状的多维数组…」] [「梯度下降是训练核心算法…」] [「Transformer 的基础架构…」]
```

切块粒度是艺术：太大（检索命中但窗口装不下、信息稀释），太小（语义不完整）。教学版用「每段一条」；真实系统常见 200~500 token 一块，块间留重叠。

---

## 5.3 链路第二步：向量化（教学版 = 字符 n-gram）

检索的前提是「能比较两个文本像不像」。真实系统用预训练 embedding 模型把文本编码成向量；**教学版用字符 n-gram 计数**——本质一样，都是「把文本变成向量，用向量距离衡量相似度」：

```
「梯度下降是训练的核心算法」
   ↓ 统计相邻字符对（bigram）
{「梯度」:1, 「度下」:1, 「下降」:1, 「降是」:1, …}
   ↓ 再加 trigram，归一化
{「梯度」:0.12, 「度下」:0.12, …, 「梯度下」:0.08, …}
```

**为什么 n-gram 能工作？** 语义相近的文本会共享大量「字符组合」：问「梯度下降是什么」和知识库里「梯度下降是训练核心算法」都含「梯度」「度下」「下降」——相似度自然高。真实 embedding 只是把「字符组合」升级成「语义组合」（「猫」和「猫咪」都映射到附近的向量）。

**归一化为什么必要？** 长文本 n-gram 数量天然多，不归一化的话「越长越像」——归一化后向量只保留「内容构成」，与长度无关。

---

## 5.4 链路第三步：余弦相似度检索

两个归一化向量的余弦相似度 = 点积（因为范数都是 1）。教学版直接线性扫描全部块（知识库小无所谓）；真实系统用向量数据库（FAISS/Chroma）做近似最近邻（ANN）搜索，亿级向量毫秒返回。

```python
hits = store.retrieve("什么是梯度下降", k=3)
# [('梯度下降', '梯度下降是训练神经网络的核心算法…', 0.17),
#  ('反向传播', '反向传播沿着计算图…', 0.09), …]
```

**注意 top-k 的选择**：k 太小可能漏掉关键信息，k 太大 prompt 被噪音填满。3~5 是常见默认值。

---

## 5.5 链路第四步：拼 prompt + 生成

检索到的文档拼成一个「开卷试卷」：

```
【背景知识】
[梯度下降] 梯度下降是训练神经网络的核心算法。先计算损失…
[反向传播] 反向传播沿着计算图…
【问题】什么是梯度下降
【回答】根据以上背景知识回答：
```

然后把 prompt 交给第 4 章的推理引擎。**模型不需要「知道」答案，只需要「读懂并复述」上下文——这正是 RAG 对模型能力要求不高也能工作的原因。**

**⚠️ 诚实说明（重要）**：本章用的是第 3 章唐诗训练的小模型，它没学过知识库文本，生成的「回答」质量有限（可能只是拼接）。**RAG 的机制是对的，但「把检索内容用得好」需要足够强的模型**——这正是大模型时代 RAG 能成立、小模型时代没人用 RAG 的原因。你在真实应用里用的是 API 大模型 + 同样的链路。

## 5.6 动手实验

1. **换问题**：`--query` 换成「什么是注意力机制」「BPE 是什么」等，观察检索命中和生成差异。
2. **换知识库**：把 `KNOWLEDGE_BASE` 换成你自己的文档（比如你的一篇 CSDN 文章拆成几段），做成「个人知识问答」。
3. **k 值实验**：`--k 1` vs `--k 5`，对比生成质量——找找「检索噪音」何时开始伤害回答。
4. **（进阶）换 embedding**：用 torch 实现一个简单的词向量平均（把每个汉字 hash 到 64 维随机向量再平均），对比 n-gram 的检索结果差异。
5. **（进阶）接真实向量库**：pip 装 `chromadb`，把知识库灌进去，用同样的 query 检索，对比命中质量和速度。
