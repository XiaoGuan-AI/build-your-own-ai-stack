## 9.1 从 CLI 到服务：为什么需要 HTTP

第 8 章的助手是命令行程序——只有「坐在电脑前的人」能用。**HTTP 服务 = 把能力开放给一切**：网页、手机 App、别的程序、别的电脑。

```
CLI：  人 → 终端 → 助手            （一个人用）
HTTP：  网页/App/程序 → HTTP → 助手  （所有人用）
```

本章用**纯标准库**实现（`http.server`），不引框架——目的和前面所有章节一致：**先看清 HTTP 服务的最小内核**。真实产品换 FastAPI 只是换壳，协议和设计完全一样。

---

## 9.2 极简服务的设计要点

**① 模型只加载一次。** `AssistantHandler.assistant` 是类级变量，所有请求共享——加载 6 秒的模型不能每个请求重载一次。这是「服务」和「脚本」的本质区别：**脚本是一次性运行，服务是常驻内存**。

**② 并发用线程池。** `ThreadingHTTPServer` 每个请求一个线程——生成是 CPU 密集长操作，单线程会卡死其他请求。真实系统：GPU 推理服务器（vLLM/TGI）用 continuous batching，几十上百请求同时算。

**③ 协议层错误处理。** 参数缺失/JSON 非法 → 结构化 400 错误。**服务的第一课：永远假设调用者会乱来。**

**④ 结构化响应。** `{"text": ..., "time_ms": ...}`——带上耗时等元数据，客户端才能做监控。**接口返回什么，是产品决策，不只是技术决策。**

## 9.3 性能优化清单：教学版 vs 生产版

| 优化项 | 教学版（已做）| 生产版 |
|--------|-------------|--------|
| KV Cache | ✅ 第 4 章 | ✅ 必须 |
| 采样控制 | ✅ temperature/top-k/top-p | ✅ 加 repetition-penalty |
| 并发 | ✅ ThreadingHTTPServer | vLLM continuous batching |
| 模型精度 | ❌ FP32 | FP16/BF16/INT8 量化（省显存 2~8 倍）|
| 批处理 | ❌ 单请求 | 动态批（相似长度请求合并前向）|
| 缓存 | ❌ 无 | prompt 前缀缓存、结果缓存 |
| 部署 | ❌ 单机单进程 | 多副本 + 负载均衡 + 监控告警 |

**看懂这张表 = 看懂推理优化的全貌**：前三行你已经亲手做过，后四行是「同一件事的工程化」——概念没变，规模变大。

## 9.6 检验点（Checkpoint）

2. 「单线程服务器对 CPU 密集的推理任务就够了，不需要并发。」 —— 对 / 错
3. 「KV Cache 是生产推理的必备优化，教学版已经实现了它。」 —— 对 / 错
4. 「服务接口返回结构化错误（400 + JSON）比返回空响应更好。」 —— 对 / 错
5. 「发布开源项目 = 把代码推上 GitHub 就完了。」 —— 对 / 错

**编程题（每题 15 分钟）：**

- **A**：给 `/generate` 加 `max_new_tokens` 参数（从请求体读取并传给助手），验证超长生成被限制。
- **B**：实现「请求日志」：把每个请求的 prompt/耗时/结果长度写入 `logs/` 下的 CSV。
- **C**：实现 `GET /stats`：返回累计请求数、平均耗时、最慢请求。
- **D**：实验 9.3 的批处理：两个请求合并成一个 batch 前向（提示：`torch.cat` 两条 prompt，注意长度对齐）。
