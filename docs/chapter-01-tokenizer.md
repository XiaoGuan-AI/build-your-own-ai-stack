## 1.1 为什么需要分词器？

大语言模型不吃文字，它吃**整数**。所以任何文本进门的第一件事，都是被切成一个个 **token**，每个 token 映射成一个 id。整个链条是：

```
"我爱深度学习"  --分词-->  [token, token, ...]  --查表-->  向量序列  -->  Transformer
```

**三个朴素的方案，各有各的死穴：**

| 方案 | 做法 | 死穴 |
|------|------|------|
| 字符级 | 每个字符一个 token | 太浪费：每个 token 信息量极小，序列变得巨长，模型算力全耗在「拼字」上 |
| 词级 | 每个词一个 token | 词表爆炸（几十万~几百万），且**未登录词 OOV**：新词、人名、emoji 直接哑火 |
| **BPE（胜出）** | 常见词=1 个 token，罕见词=拆成子词，再不济=拆到字符 | 词表可控（几万），**没有 OOV**——任何输入都能拆干净 |

**BPE 的另一个隐藏优点：训练和解码完全无损。** encode 出的 id 序列能 100% 还原成原文。这保证了模型输出的整数序列永远能翻译回人能读的文字。

## 1.2 BPE 直觉：一个例子走一遍

GPT 论文里的经典例子，文本只有 5 个词不断重复：

```
low low low low low low low low lowest lowest lowest newer newer newer newer newer newer newest newest newest
```

BPE 从「字符」开始：

```
第 1 轮合并：统计所有相邻字符对
  "lo" 出现 19 次（8 个 low + 3 个 lowest = 11 次？不，让我们认真数）
```

放心，我们不用手数——**算法自己数**。BPE 做的事情只有一件，循环做：

```
重复直到词表达到目标大小：
    1. 统计所有相邻对的频率
    2. 找出频率最高的一对 (a, b)
    3. 把 (a, b) 合并成新符号 ab，整个文本里所有 (a, b) 都替换成 ab
```

几轮之后你会看到：`w` 和 `e` 先合并成 `we`（出现频率最高），`l` 和 `o` 合并成 `lo`…… 跑 `python code/ch01/bpe.py --demo` 看完整合并过程。**注意：在本语料里，`lowest` 最终被拆成 `lo` + `west` 两个 token，而不是合成一个——具体怎么拆，完全由语料的频率决定。** 换一份 `lowest` 出现频率高得多的语料，结果就不同。这正好暴露了一个工程问题：不加约束，**空格也会参与合并**（demo 里能看到 `w lo` 这种跨词 token）——这就是真实系统需要 pre-tokenization 的原因（见 1.5 实验 4）。

> **直觉锚点**：BPE = 把文本里「最常见的拼写组合」收编成「一个代号」。像极了词典编撰：常用字组词入典，生僻组合拆开解释。

## 1.3 代码逐段讲解

打开 `code/ch01/bpe.py`，跟着下面的地图读。

### 数据结构（三个字典/列表，就这么简单）

```python
char_to_id : 字符 -> id      # 初始词表（训练时从文本收集所有字符）
vocab      : id  -> 文本     # 完整词表 = 字符 + 所有合并出来的新符号
merges     : [(a,b), ...]    # 合并规则，按学习顺序保存
```

### 训练（`train`）——学合并规则

```python
# 初始词表：文本里出现过的每个字符一个 id
chars = sorted(set(text))
self.char_to_id = {c: i for i, c in enumerate(chars)}

# 把文本转成 id 序列，然后循环合并
ids = [self.char_to_id[c] for c in text]
for _ in range(可合并的次数):
    pair_freqs = Counter(zip(ids, ids[1:]))     # ① 统计相邻对频率
    (a, b), freq = pair_freqs.most_common(1)[0] # ② 最频繁的一对
    new_id = len(self.vocab)                    # ③ 新符号 = 词表末尾的下一个 id
    self.merges.append((a, b))
    self.vocab[new_id] = self.vocab[a] + self.vocab[b]   # 新符号文本 = 拼接
    ids = self._merge_pair(ids, (a, b), new_id) # ④ 全文替换
```

**一个容易懵的点**：合并发生在 id 层面，而不是字符层面。`low` 是一个 id，`e` 是一个 id，合并 `(low, e)` 得到新 id，它的文本是 `"low" + "e" = "lowe"`。**合并规则永远只作用于相邻 id 对。**

### 合并操作（`_merge_pair`）——贪心扫描

```python
while i < n:
    if 当前位置是 (a, b):    # 匹配上
        out.append(new_id); i += 2   # 吞掉一对
    else:
        out.append(ids[i]); i += 1   # 不匹配，原样保留
```

注意这个「贪心」：从左到右扫，**能合就合**。为什么不会出歧义？因为编码时我们**按训练的顺序应用合并规则**——训练时第 k 轮合并出的符号，编码时就在第 k 次应用。顺序一致，结果就一致。

### 编码（`encode`）——把规则用回去

```python
ids = [self.char_to_id[c] for c in text]      # 先拆成字符
for new_id, (a, b) in enumerate(self.merges, start=len(self.char_to_id)):
    ids = self._merge_pair(ids, (a, b), new_id)   # 按训练顺序重放合并
```

### 解码（`decode`）——查表拼接，一行

```python
return "".join(self.vocab[i] for i in ids)
```

## 1.4 三个关键设计决策（面试也爱问）

**① 为什么用「字符」起步，不用「词」起步？**
字符是语言的「原子」，任何文本都能拆到字符，所以**初始词表永远覆盖全集**——这是「没有 OOV」的根基。从词起步的话，词表要么封顶（有 OOV），要么无限涨。

**② 为什么 GPT-2 用 byte-level BPE（字节起步）？**
字符起步有个漏洞：Unicode 字符上万个，而且未来还会加。GPT-2 的解法是**从 256 个 UTF-8 字节起步**——任何字符都能用字节表示，所以词表锁死为 256 + merges，还能无损往返。**这是工程版和你这版唯一的本质区别**（练习 3 让你补上它）。

**③ 为什么中文模型词表动辄 10 万+？**
中文信息密度高：一个汉字就是完整语义。词表太小 → 中文被拆成碎片 token → 序列变长、算力浪费、生成变慢。所以中文 LLM 普遍把词表扩到 10 万~20 万（英文模型一般 3 万~5 万）。你现在可以自己验证：把同一句话用不同 `vocab_size` 训练，对比压缩率。

## 1.5 动手实验

1. **压缩率曲线**：用本章 demo 的语料，分别用 `vocab_size=64 / 128 / 256 / 512` 训练，记录压缩率，画一条曲线。你观察到什么规律？（提示：收益递减）
2. **中文 vs 英文**：分别对一段纯中文和一段纯英文文本训练，比压缩率。解释为什么中文在相同词表下压缩率更高。
3. **（进阶）byte-level 化**：把 `train` 的初始词表从「字符」改成「UTF-8 字节」——文本先 `text.encode("utf-8")` 成字节序列，`decode` 时先按字节还原再 `.decode("utf-8")`。改完你就拥有一个完整的 GPT-2 式分词器了。
4. **（进阶）预切分（pre-tokenization）**：GPT-2 在 BPE 之前还会按空格和标点预切分，防止跨词合并。思考：不预切分的话，「hello world」里的 `lo` 会被哪个词教坏？
